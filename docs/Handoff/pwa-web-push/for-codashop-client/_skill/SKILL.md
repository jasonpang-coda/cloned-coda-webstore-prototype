## Overview

Translate a prototype handoff bundle into changes on **existing** components in this
repo. This is the cross-codebase sibling of `figma-implement-design`: that skill reads a
live Figma frame; this one reads a spec generated from a different Vue codebase (the
COD:M web store prototype) that is **not 1:1** with this repo — different framework
conventions (scoped-CSS-decoy vs Tailwind `@apply`), different token file layout, same
`--x-*` token namespace.

- **Primary:** styles and component logic on the **existing** components `file-map.md`
  names — the bundle is generated specifically because those components already exist.
- **New Vue components:** discouraged by default, same as `figma-implement-design`. A
  handoff bundle whose `file-map.md` has no row for something means it's new — **stop and
  ask** before creating it.
- **Tokens:** never transcribe a prototype token literally. `tokens.md` has already
  cross-referenced every token this feature touches against this repo's real
  `assets/css/sitebuilder/tokens/` set — use its classification, don't re-derive one.

### Where this file may live

- **Canonical copy:** wherever this repo settles it — recommend
  `skills/implement-handoff-spec/SKILL.md`, matching `figma-implement-design`'s location.
- **Cursor:** mirror it at `.cursor/skills/implement-handoff-spec/SKILL.md` (symlink to
  the canonical file, same pattern `figma-implement-design` already uses) so Cursor
  auto-discovers it without a second copy to keep in sync.
- Add a one-line pointer from this repo's `AGENTS.md` — `figma-implement-design` already
  anticipates this ("point rules or prompts at `skills/...`, or add a one-line pointer
  from your product's config") but no pointer for either skill exists there yet.

## How to read a handoff bundle

Every bundle has five files, meant to be read in this order:

1. **`AGENTS.md`** — the entry point. States the hard rules for this specific feature and
   the read order for the rest. Read this first, always.
2. **`house-rules.md`** — this repo's own standing conventions (i18n, no tenant
   branching, edge-only tokens, motion-by-intent, no new components without permission,
   test tiers), cited to source. Not restated elsewhere in the bundle — if it's not here
   and not in your own `AGENTS.md`/`.cursor/rules/`, it isn't a rule.
3. **`file-map.md`** — one row per component: which existing `.vue` to edit, which
   mirrored `assets/css/sitebuilder/components/**` file its styles belong in, which i18n
   key prefix its copy should use.
4. **`tokens.md`** — the token crosswalk (see below — this is the step
   `figma-implement-design`'s "token existence verification" corresponds to, done ahead
   of time by the generator instead of by you).
5. **`spec.md`** — states, transitions, choreography, and (when the feature has one) an
   Integration contract section describing platform/backend behaviour the UI must react
   to, without prescribing how that backend is built.

## Token-existence verification — already done, read the verdict

`figma-implement-design` makes you verify token existence by hand (§"Token existence
verification (mandatory before writing styles)"). A handoff bundle's `tokens.md` has
already run that check programmatically against this repo's real token files. Four
verdicts, each with a different required action:

| Class | Meaning | What you do |
|---|---|---|
| `EXACT` | The named token exists here under the same name. | Use it as-is. |
| `RENAME` | Absent by that name; this repo has the same role under a different name. | Use the name `tokens.md` gives — don't reintroduce the prototype's name. |
| `NEW_SEMANTIC` **(gated)** | Absent, and it's a semantic-tier token (`--x-bg-*`, `--x-text-*`, `--x-border-*`, `--x-pad-*`, `--x-gap-*`, `--x-radius-*`, `--x-size-*`). | **Do not add it.** This repo's semantic tiers are a closed set, same rule as the prototype's own `web-store-tokens` skill §2b — a new one needs the design-system owner's sign-off. Use the row's `fallback` token until that lands. |
| `NEW_EFFECT` | Absent, but it's an effect/extension-tier token (shadow/glow/blur). | Exempt from the closed-set rule — may add directly to the file `tokens.md` recommends, on the `theme-preset-edge--*` branch per `sitebuilder-edge-only-tokens.mdc`. A fallback is still listed if you'd rather not add it yet. |

A `tokens.md` with **zero** `NEW_SEMANTIC` rows unresolved is what "token verification
passed" looks like for a handoff bundle — same bar as `figma-implement-design`'s own
step, just pre-computed.

## The two-file rule

Every component in this repo splits its markup from its CSS: the `.vue` file's
`<style scoped>` block is a single `@use '@commerce-styles/components/...'` re-export: the
actual rules live in the mirrored `assets/css/sitebuilder/components/**` path
`file-map.md` names. A handoff feature almost always touches **two files per component**,
not one — editing only the `.vue` and expecting styles to apply will silently do nothing.

## i18n

Every string the bundle's `spec.md` shows in the prototype's UI must become an i18n key
under the prefix `file-map.md` gives that component, following
`.agents/skills/add-translations`'s file map (`i18n/locales/en.json`,
`translations-api/src/assets/{en,template}.json`, key constant files, WireMock fixtures).
Never hardcode the copy from the spec directly into a template.

## Definition of done

- Every state in `spec.md` §2 (and every row of its Integration contract, if present) is
  reachable and matches the reference — cross-check against the deployed prototype's
  `/handoff/<slug>` page if a `demo_url` is given, since a bundle is a snapshot and that
  page is the live source of truth.
- Every token in `tokens.md` is either cited exactly (`EXACT`/`RENAME`) or its
  `NEW_SEMANTIC` fallback was used pending sign-off — none guessed.
- Copy runs through i18n, not hardcoded.
- `npm run lint`, `npm run format:check`, and the lightest sufficient test tier pass.
- Report results against `spec.md`'s own verification checklist, not as free prose.
