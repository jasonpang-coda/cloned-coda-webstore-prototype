# Release Notes — v0.49.1

**Date:** July 2026
**Milestone:** Fix a runaway-timer bug that broke the Codashop TrustBar carousel on Vercel Production

---

## Highlights

- **Fixed the TrustBar carousel/rotator running ~1000× too fast.** Reported by the user against the deployed Production build (`coda-webstores-prototype.vercel.app`) as "the carousel doesn't show the content" and "there is a transition issue." Root-caused live in the browser: `TrustBar.vue`'s publisher-logo rotator and carousel auto-advance both read their interval from a CSS custom property (`--motion-trust-rotate-interval`, `--motion-trust-carousel-interval`) via `getComputedStyle(...).getPropertyValue(...)` and parsed it with bare `parseInt(value, 10) || fallback`. `getComputedStyle` normalizes whole-second `<time>` values to `s` units — a token declared `5000ms` computes back as `"5s"`, not `"5000ms"` — and `parseInt("5s", 10)` returns a *truthy* `5`, so the intended fallback never caught it. Both timers ended up firing every ~2–5 **milliseconds** instead of every 2.6–5 **seconds**: the active card's content never stayed visible long enough to read, and the publisher-logo crossfade `<Transition>` got stuck with overlapping enter/leave classes since its 350ms fade never had time to complete between ticks.
- **New shared helper, `src/composables/useCssTimeMs.js`.** `cssTimeToMs(value, fallback)` checks for an `ms` suffix before assuming the value is in seconds and multiplying by 1000 — correctly handles whatever unit `getComputedStyle` happens to serialize a `<time>` value as. Applied at both `TrustBar.vue` call sites and at the one other place in the codebase with the same latent pattern, `NavDrawer.vue`'s post-close-navigate delay (`--motion-sys-duration-exit`) — that one was not currently causing a visible bug (its `200ms` token computes to `".2s"`, and `parseInt(".2s", 10)` returns `NaN`, which correctly fell through to the fallback), but the same fragile assumption was there and is now fixed for robustness.
- **Verified live, not just by reading the diff:** confirmed via direct DOM/state inspection in the browser that `--active` (the carousel's transform-driving CSS var) now advances by exactly one step roughly every 5 seconds, matching the intended interval, and that card content renders and stays legible at rest.

## Changes

### `src/composables/useCssTimeMs.js` (new)

- `cssTimeToMs(value, fallback)` — parses a computed CSS `<time>` string to milliseconds, correctly handling both `s` and `ms` serializations.

### `src/components/TrustBar.vue`

- `startPubRotator()` and `resetCarouselTimer()` now use `cssTimeToMs(...)` instead of `parseInt(...) || fallback` to read `--motion-trust-rotate-interval`/`--motion-trust-carousel-interval`.

### `src/components/NavDrawer.vue`

- `onItemClick()`'s post-drawer-exit navigation delay now uses `cssTimeToMs(...)` to read `--motion-sys-duration-exit`, same fix applied preemptively (not currently broken, but the same fragile pattern).

### `docs/component-breakdown.md`, `docs/Handoff/trust-bar/README.md`

- Footer bumped with the bug/fix summary; the handoff's §1.1 choreography timeline and §3.7 token contract updated with the corrected line citations and a new callout documenting the bug and its fix, so a rebuild elsewhere doesn't reproduce the same `parseInt`-on-a-CSS-time-value mistake.
